Let the language model read, let the validated code compute: WebSemantic

Step 4 of 5 · AI in its placeSee it on the thread

Language models help people use validated tools; the calculation, the checking and the responsibility stay with validated codes and people. Every tool, at the periphery.

Ask for a scientific simulation in plain words, without an AI guessing the missing values. WebSemantic lets the language model translate the request into variables, asks the person for whatever is missing, and leaves every number to a validated, pinned scientific code.

Cyril Voyant · Mines Paris – PSL, Centre O.I.E.

In brief

  • A language model reads a written request very well, but readily fills in what was not said. In a scientific calculation, a guessed value gives a result that looks precise and may be wrong.
  • WebSemantic separates three roles: the language model translates words into variables; a validator decides to execute, clarify or refuse; a validated, unchanged code computes every number.
  • Every result comes with its units, the origin of every input and the exact version of the code: it can be rerun and checked.

The problem, and for whom

Validated scientific codes are precise but demanding: each parameter, its unit and its bounds must be known. An engineer sizing a road tunnel, a radiotherapy researcher comparing two treatment schedules, a teacher showing a model to students do not always have that time. Language models offer a shortcut: "simulate one week for a short tunnel with light traffic". The risk is that they fill the gaps themselves: "a weak updraft" becomes 0.1 m/s, "the usual dose" becomes 3 Gy (the gray, unit of absorbed dose), and the code runs on values nobody stated.

The question is therefore: how can we use plain-language reading without losing what makes a validated code valuable, namely known inputs and traceable results?

The idea: from text to a verifiable result

Step Who acts What comes out
1. Text The person A request in English or French
2. Variables The language model The code's variables, each with its unit, its origin and the words that justify it
3. Decision The validator Execute, clarify (a question to the person) or refuse
4. Calculation The validated, pinned code The numbers, and only it
5. Record WebSemantic Tables, units, origin of every input, code version and file fingerprints

The core is the contract: a description, written once per code, of each variable (meaning, unit, bounds, default value, accepted everyday words). The same description produces the contract read by the language model, the checking rules and the citation metadata: one definition, several uses.

What the language model does, and what it does not

It does It does not
Read the request and restate it in three sentences Compute any result
Link each word to a variable of the contract Invent a value absent from the request
Convert a stated unit (2 km → 2000 m) Choose a default or a convention alone: it proposes, the person accepts
Ask when a word is ambiguous Change the scientific code or its assumptions
Report a conflict between two values Decide for the person

If the language model makes a mistake, the validator stops it: a value without an origin, an inconsistent unit or a bound that is exceeded prevents the calculation.

Definitions

Term Definition
Language model A neural network trained on large text corpora, which predicts and produces text.
Contract The reading rules of a code: meaning, unit and bounds of each variable, what may be proposed by default, what must be asked.
Origin of an input Where the value comes from: stated by the person, unit conversion, declared default, qualitative convention. The last two count only once accepted.
Qualitative convention The value the contract attaches to an everyday word, parameter by parameter ("short tunnel" → 375 m). It is proposed, never imposed.
Validator The program that checks a scenario and returns one decision: execute, clarify or refuse. It never invents a value.
Validated, pinned code A published, checked code used without modification at a precise version; its files are checked against a fingerprint (SHA-256) before each run.
Provenance The record of where each number comes from: inputs, the person's agreement, code version.
EQD2 The total dose which, given in 2 Gy fractions, would have the same biological effect as the schedule studied.

A simulated example, step by step

Road tunnel (Tunnel Load Simulator, TLS). Request: "Simulate one week of electricity demand for a short twin-tube tunnel, LED lighting, light traffic."

  • "one week" → 7 days, stated; "twin-tube" → 2 tubes, stated;
  • "short tunnel" → 375 m, proposed convention; "light traffic" → traffic level 0.3, proposed convention;
  • "LED lighting": the contract knows "LED adaptive" and "LED fixed". The word is ambiguous: clarify, and the question is asked;
  • the other variables (ventilation, altitude…) receive their declared defaults, shown to the person.

Once the person has chosen the lighting and accepted the conventions and defaults, the decision becomes execute. TLS, and TLS alone, returns the energy, the peak power and the load factor, with their units and the list of inputs. A request to certify the consumption of a real tunnel is refused: it is outside the code's domain.

Radiotherapy, fictitious case (LQL-Equiv). Complete scenario: rectum (organ at risk) and prostate (target), 39 fractions of 2 Gy, every input stated and accepted. Decision: execute; LQL-Equiv returns an EQD2 of 78.0 Gy. The result can be checked by hand: at 2 Gy per fraction, the EQD2 equals the total dose, 39 × 2 = 78 Gy. Remove the dose per fraction: the decision becomes clarify, and nothing is computed. When two schedules are compared, the best schedule in WebSemantic is an equivalent one (same EQD2, computed by LQL-Equiv), not one chosen from a complication probability.

First results (preliminary)

These figures come from an evaluation that has not yet been published. Each one is a preliminary, unpublished result (paper in preparation) and may change.

  • Why guessing matters. In simulations of plausible numerical readings of the same vague words, the guessed values changed a computed result by up to a factor of 2.6, and moved a normal-tissue complication probability (NTCP) from 3 % to 47 %. Preliminary, unpublished result (paper in preparation).
  • What the contract changes. On 78 cases, each asked with and without the contract, three times, a premature calculation (one launched before every required input was stated or accepted) became less frequent when the contract was added to the documentation: from 26 % to 6 % (Mistral-Small), 17 % to 1 % (Qwen2.5), 52 % to 23 % (Codestral) and 25 % to 3 % (Gemini). Preliminary, unpublished result (paper in preparation).

The NTCP figure only shows how much a guess can move a result. It is not a criterion: in WebSemantic, the best schedule is judged by equivalence (same EQD2), not by NTCP.

Where it sits on the complexity ladder

The complexity ladder ranks methods from direct calculation (bottom rung) to deep networks (top rung). WebSemantic uses the top rung to read: the language model is a deep network. The calculation stays at the bottom, in direct calculation (LQL-Equiv) and simulation (TLS). AI: essential in the toolbox, never mandatory in the solution.

Limits, and what remains to be shown

  • A valid scenario does not guarantee that the request was understood, nor that the scientific model suits the question: the three-sentence restatement is there for the person to check.
  • The validator is only as good as the contract: a word absent from its tables has no value, and the machine asks.
  • LQL-Equiv is for research and teaching, on fictitious scenarios. It is not a medical device; no patient data is used; the practitioner decides.
  • The first results above are preliminary and unpublished (paper in preparation): they may change after peer review.
  • In the web app, the request's words are sent through a relay to an external language model (Mistral); the calculations run in the browser.
